# CombatStand: запуск и фактическая приёмка

Это отдельный технический стенд, не замена `places/BrickToads.rbxlx`. Код не содержит ROM, исходного ASM, чужой карты или ресурсов оригинала. Сборка XML, успешные контракты Lua/Luau и компиляция не являются запуском Roblox. Статусы ниже относятся к конкретным зафиксированным прогонам; расширять их на непройденные сценарии нельзя.

## Получить сборку

Из корня репозитория выполнить `python tools/build_combat_stand.py`. Получится `build/CombatStand.rbxlx`. Флаг `--check` сверяет уже собранный файл с исходниками. GitHub workflow `Combat stand checks` также сохраняет place, SHA-256 и вывод контрактных тестов как артефакт своей конкретной ревизии.

На подготовленном Windows workspace переносимые CLI лежат внутри проекта:

```powershell
& .\.tools\python-3.13.9\python.exe tools/build_combat_stand.py
& .\.tools\python-3.13.9\python.exe tools/test_combat_stand.py
& .\.tools\luau-0.745\luau.exe tests/run_stand.luau
```

Открыть этот файл в Roblox Studio. Сначала запустить Server & Clients с двумя клиентами. На первом подключённом клиенте нажать **Старт** после появления обоих. Состав фиксируется на момент старта: первые 1–3 подключённых пользователя. Поздний новый пользователь только наблюдает; возвращающийся прежний владелец получает свою роль в той же живой серверной сессии. Отдельный новый запуск после поражения выдаёт новый состав/ресурсы.

Управление: WASD либо сенсорная площадка слева; F / «Удар», R / «Таран», Space / «Прыжок». Камера следует Humanoid; серверные модели специально не назначаются Player.Character. Телефон/планшет нужно испытать отдельно: видимые touch-кнопки не доказывают проверенную мобильную пригодность. Движения/атаки пока без авторских анимаций; подсветка показывает попадание/защиту.

## Что является точным, а что экспериментом

Боевой raw Life хранится отдельно. Удар: 47→43→47 после лёгкой реакции. Таран: 47→31, 16→15, а при 15 выбирается смертельный профиль 21. Арифметическое получение нуля без underflow не означает смерть. Проверяется общая разрядная формула; полнота всех действий/состояний оригинала не заявляется.

Пять сердец показывают дробное `5 * rawLife / 47`. Это **предложение отображения для стенда**, не окончательно утверждённый перенос BT-33. Humanoid.Health служит только физическому телу и не хранит raw Life.

`Config.lua` явно содержит `EXPERIMENTAL_STAND_ONLY`: скорость/прыжок, размеры контакта, startup/window/cooldown, время реакции и задержка подтверждённой смерти — настройка стенда, не измеренные параметры оригинала. Импульсы задают добавку скорости в studs/s через `AssemblyMass`: профиль 18 — 9/0 по горизонтали/вертикали, 22 — 32/18, 21 — 34/27. Различие профилей сохранено, точная 3D-калибровка не принята. Полной анимации тарана и отдельного разбега атакующего нет: это ограниченный стенд контакта/реакции.

Обычный щит блокирует боевое повреждение на 2 секунды, но здесь не вводит иммунитет к смещению или смертельной геометрии. Аварийный щит держит тело до 10 секунд, снимается допустимой собственной атакой либо безопасным переносом; таймаут расходует ещё одно возрождение только при доступном запасе и подключённом владельце. Эти правила переноса — не доказательство исходного NES-счётчика защиты.

## Подготовка воспроизводимых сцен

Только в **серверной** Command Bar Studio доступен `game.ServerScriptService.CombatStand.Diagnostics`, BindableFunction. Клиенты не имеют такой команды; вне Studio объект не создаётся. Подготовка требует живых неподвижных героев без щита/реакции/начатой атаки. Номер P соответствует внутреннему слоту, не Roblox UserId.

Для обычного удара: `game.ServerScriptService.CombatStand.Diagnostics:Invoke("Case", "Safe", 1, 2)`, затем нажать F у P1. Для обратной роли подготовить ту же сцену со слотами 2,1.

Для края: `game.ServerScriptService.CombatStand.Diagnostics:Invoke("Case", "Edge", 1, 2)`. Цель стоит возле края основной площадки; нажать F у атакующего и записать реальный исход. Это сценарий проверки экспериментального масштаба, **не заранее гарантированный PASS**. Если падения не происходит или цель падает без удара, сохранить FAIL и калибровать сцену отдельно.

Для переходов тарана: `game.ServerScriptService.CombatStand.Diagnostics:Invoke("Case", "Dash16", 1, 2)` либо `"Dash15"`, затем R. Подготовка `"Safe"` + R проверяет начальный Life=47. После реакций можно повторять подготовку. Весь доверенный ввод диагностики помечается в серверном журнале.

Для аварийного появления: `game.ServerScriptService.CombatStand.Diagnostics:Invoke("NoSafe", true)` отключает столкновения разрешённых опор. После падения должен появиться удерживаемый герой. `...:Invoke("NoSafe", false)` возвращает опоры и позволяет проверить перенос без дополнительной жизни/лечения/двухсекундного щита. Оставить NoSafe включённым для циклов 3→2→1→0; отдельно атаковать под аварийным щитом. Ноль сам по себе не должен убивать живого героя.

`...:Invoke("Reset")` возвращает стенд в лобби; это только диагностический сброс, не игровой respawn. `print(game.ServerScriptService.CombatStand.Diagnostics:Invoke("Dump"))` выводит JSON состояния и последних 256 событий. Сохранять полный Server Output заранее: старые записи вытесняются из кольцевого буфера.

## Матрица приёмки

### Автоматизация через Roblox Studio MCP

Многоклиентский запуск доступен программно через `StudioTestService:ExecuteMultiplayerTestAsync`; ручная работа с вкладкой Test не требуется. Обычный MCP `start_stop_play` запускает одиночный Play, а `StudioTestService` — настоящий сервер и несколько тестовых клиентов.

1. Собрать и открыть `build/CombatStand.rbxlx`. Перед запуском через MCP проверить в Edit точное совпадение Source всех восьми скриптов/модулей с текущими исходниками, включая серверный ConnectionRegistry.
2. В отдельную несохранённую тестовую копию через `execute_luau` добавить `tests/stand/CombatStandStudioAcceptance.server.lua` как Script в ServerScriptService и `tests/stand/CombatStandStudioClient.client.lua` как LocalScript в StarterPlayerScripts. Эти файлы не включаются в production builder. Они исполняются только в Studio при `GetTestArgs().tag == "CombatStandAcceptance"`.
3. Оценить содержимое `tools/studio_launch_combat_acceptance.luau` как функцию и вызвать возвращённый launcher. Например, аргументы `{name="Baseline3", players=3, timeoutSeconds=240, networkProfile="Current Device"}` запускают матрицу всех шести направленных пар с Punch47, Dash47, Dash16 и Dash15. `{name="Protection2", players=2, protectionOnly=true, timeoutSeconds=240}` запускает отдельные проверки обеих защит.
4. Launcher возвращает управление сразу. В Edit читать `ServerStorage.CombatStandAcceptanceEvidence.<name>`: атрибут Status — RUNNING/PASS/FAIL/ERROR, Chunks и Bytes — размер результата. После завершения склеить значения `Chunk0001`, `Chunk0002` и далее по номеру и разобрать JSON. Полный результат больше 200000 байт нельзя записывать одним StringValue; launcher сохраняет UTF-8-корректные части по 6000 байт.
5. Участники автоматического прогона — реальные Studio clients. Тестовый LocalScript временно отключает штатный `CombatStandClient` в тестовой сессии, чтобы его фоновые Move-пакеты не конфликтовали с test seq. Start/Attack отправляются настоящим клиентом через Intent RemoteEvent, сервер сам выбирает цель/профиль/урон/импульс. Этот прогон проверяет сеть и физику; keyboard/touch/HUD требуют отдельного прогона со штатным клиентом.
6. Снимок `settings().Network` фиксировать до теста. Для отдельного временного прогона можно применить 4G/LTE: inbound delay45ms/jitter20ms/loss0.4%, outbound55ms/30ms/0.5%. Loss0.5 означает0.5%, не50%. Считать реальные результаты после применения и вернуть точные исходные настройки по завершении тестовой серии. Настройки сохраняются между перезапусками Studio.

Полный журнал, SHA-256 place, версии и фактически исполненные сценарии должны сохраняться в отдельном отчёте этой ревизии. Общий PASS runner не закрывает перечисленные им skipped: реальный reconnect прежнего аккаунта, физические мобильные устройства и непройденные сценарии геометрии/сети.

| Сценарий | Ожидаемая проверка | Фактический статус |
|---|---|---|
| Сервер + 1/2/3 клиента | Фиксированный состав, собственные тела/ресурсы | PASS: solo и настоящие2/3 клиента |
| Все направленные пары героев | Серверный контакт и единственный импульс, 18/22/21 | PASS:24cases/445checks, включая Dash47/16/15 |
| Стена, камера, пропасть, опасная поверхность | Причины различаются; камера не убивает | PASS: solo и неизменённый Edge до/после настоящего удара |
| Обычный/аварийный щит, атака, безопасный перенос, таймаут | Сроки, отсутствие лишнего лечения/расхода | PASS: обе защиты и3→2→1→0; отдельные protection-runs65checks каждый |
| Отключение и возврат в тот же живой сервер | Тело получает урон; владелец возвращается без лечения | PARTIAL: реальные уход/offline damage/поздний новый spectator PASS; прежний UserId не возвращён AddPlayers, pending-attack fixture не достигла нужного порядка |
| Задержка, jitter, потери, повтор/устаревшая команда | Нет второго попадания/импульса/персонажа | PASS для ограниченных матриц:4G core8cases/161checks и защиты65checks; отдельно реальные команды BT-58 —48scenarios/486checks PASS при нулевой эмуляции сети. Их совместный4G-прогон не выполнен |
| Телефон/планшет | Touch, HUD, камера, измеренная производительность | NOT RUN |

Для каждого запуска записать commit, SHA-256 place, версию Studio, 1/2/3 клиентов, устройство/ОС, сетевой профиль, подготовку, действие, ожидаемое и наблюдаемое состояние, Server/Client Output и PASS/FAIL/NOT RUN. Закрытие последнего клиента и исчезновение сервера не тестируют возврат в прежнюю живую сессию. Реальный reconnect с тем же аккаунтом и маршрутизацией в живой сервер требует отдельного испытания; сам счётчик connectionEpoch этого не доказывает.

Фактические JSON и ограничения этой ревизии: [Studio MCP report](../../reports/2026-11-06-combat-stand-studio/README.md). Для дополнительной геометрии/отключения launcher принимает `edgeDisconnectOnly=true`. Сценарий сохраняет FAIL, если Studio подтверждает отключение уже после Hit: вызов LeaveTest/Kick сам по себе не доказывает удар, разрешившийся после фактического Connection. Параметры windup и геометрия для получения PASS не меняются; отдельные Edge/offline-body результаты сохраняются даже при непройденной предпосылке pending-attack.

## Граница использования

Привязка BT-13 теперь использует актуальный объект Player, а не только UserId. Старое подключение не получает mine/epoch и не может отправлять Intent; повторные join/remove не сбрасывают состояние. Контрактные проверки: `luau tests/run_connections.luau` и `python tools/test_stand_gateway.py --luau <путь-к-native-Luau>`. Второй runner выполняет настоящий Stand Source с тестовыми сервисами/транспортом; это не авторизованный вход аккаунта Roblox. [Отчёт и границы BT-13](../../reports/2026-11-07-stand-connection-ownership/README.md).

Для настоящего возврата возможен отдельный Studio Test/Team Test маршрут A→B→тот же reserved A через TeleportAsync: поддержка появилась5 ноября2026 ([официальное объявление](https://devforum.roblox.com/t/test-teleports-in-studio/4977640)). Нужны места одной experience и проверка server marker/run/actor; одинаковые пустые JobId/PrivateServerId не доказывают тот же сервер. В текущем локальном файле GameId=PlaceId=0, а AddPlayers не выбирает прежний UserId. Этот транспортный gate остаётся NOT RUN.

Дополнительная проверка BT-58: инжектировать `tests/stand/CombatStandSecurityScenarios.lua` как ModuleScript `ServerScriptService.CombatStandSecurityScenarios` рядом с acceptance runner. Launcher принимает `securityOnly=true` (два клиента), а для короткой регрессии рассылки — дополнительно `securityPhase="fanout"`. Raw/Burst генерируются только тестовым клиентом; обработчик Intent остаётся производственным. Фактические два RED, исправления и финальный PASS находятся в [отчёте командной матрицы](../../reports/2026-11-07-stand-command-security/README.md). Эта проверка не включает настоящий reconnect прежнего пользователя, мобильные устройства или будущие NPC/босс/маршрутизацию.

Не переносить диагностический стенд в публичный продукт без ревью/приёмки. Серверное владение телами выбрано для контроля исходов; измерение тестового клиентского канала и пройденные физические сценарии записаны в отчёте. Плавность игры на целевых устройствах и численные NFR-бюджеты ещё требуют измерений. Проверка типов всех Roblox API, полная игровая приёмка, весь первый уровень, NPC, босс, захваты/оружие и человеческие враги этим ограниченным результатом не закрываются.

Официальные справки: Roblox Creator Hub — `scripting/security/client-server-boundary`, `physics/network-ownership`, `studio/testing-modes`, `studio/network-simulator`. Они не заменяют журнал этой сборки.
